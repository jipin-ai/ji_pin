# BidSmart v1.0 架构重设计

> 理论基础: Legal-DC (2603.11772) + Adaptive HR (2604.14222) + Agents-as-Judge (2506.22485) + Reason and Verify (2603.10143)

## 核心变更

从「匹配→审查」两步流水线 → **六阶段分层验证管线**。

## 新架构

```
┌─────────────────────────────────────────────────────────┐
│                    Stage 0: 结构化解析                      │
│  tender_doc → 编号层级树 (3.1 → 3.1.1 → 3.1.2)          │
│  bid_doc    → 编号层级树 (第三章 → 3.1 → 3.1.2)          │
│  输出: 条款-章节编号映射表                                  │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│              Stage 1: 多策略匹配（三路并行）                  │
│  Path A: 结构化对齐 (编号映射 3.1→3.1, 差距=0)             │
│  Path B: 语义匹配 (BGE embedding, cosine sim)            │
│  Path C: 关键词匹配 (BM25, exact keyword hits)            │
│  → Merge: 三路结果加权融合 → 候选段落 + agreement_score     │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│             Stage 2: 双路径反思验证                         │
│  Path A: "这段投标内容是否回应了该要求？" → yes/no+摘录       │
│  Path B: "这条要求应该在投标文件的哪个位置回应？" → 定位      │
│  → Cross-check: A和B指向同一段落 → 通过                    │
│  → 不一致 → 标记冲突，降低置信度                            │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│             Stage 3: 精确定位摘录                           │
│  LLM: "从匹配段落中摘录与要求直接相关的内容（≤500字）"        │
│  输出: relevant_excerpt (精确原文)                         │
│  目标: 不送3000字整段，只送500字精准内容                     │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│             Stage 4: 合规审查（带法规上下文）                    │
│  输入: 要求 + 精准摘录 + 相关法规条款 + 图片感知标记              │
│  宽松原则 + 证据导向 + 法规引用                                 │
│  输出: verdict + reason + suggestion + confidence             │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│          Stage 5: 交叉验证（red级条款）                      │
│  对 red 级条款: 同一输入→两次独立审查→对比判定                │
│  一致 → 确认; 不一致 → unable_to_judge                    │
│  目标: 消除 LLM 随机性导致的假阴性                           │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│            Stage 6: 聚合 + 风险评分                         │
│  按权重分层 (red/yellow/amber)                              │
│  区分「证据不足」vs「证据否定」                                │
│  交叉验证一致性报告                                         │
└─────────────────────────────────────────────────────────┘
```

## 四层缺失 vs 解决方案

| 缺失层 | 论文依据 | v1.0 方案 |
|--------|---------|----------|
| 结构化对齐 | Legal-DC clause-boundary + Adaptive HR Tree Reasoning | Stage 0+1: 编号层级树 + 三路匹配 |
| 双路径反思 | Legal-DC dual-path self-reflection | Stage 2: A/B 双路径交叉验证 |
| 精确定位 | Reason and Verify | Stage 3: LLM 摘录 ≤500字 |
| 交叉验证 | Agents-as-Judge 95% | Stage 5: red级双审对比 |

## 与 v0.9 对比

| 维度 | v0.9 (当前) | v1.0 (新架构) |
|------|------------|--------------|
| 匹配策略 | 1路 (BGE) | 3路融合 (结构化+BGE+BM25) |
| 验证 | 1路软验证 | 2路硬交叉验证 |
| 审查输入 | 3000字整段 | ≤500字精准摘录 |
| 法规上下文 | 无 | 加载法规条款 |
| 一致性保证 | 无 | red级双审交叉验证 |
| 预期精准度 | ~30% | 85-93% |
