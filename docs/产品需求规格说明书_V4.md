## 1. 产品概述

### 1.1 产品定义

**通睿 AI 安全网关**（Tongrui AI Secure Gateway）是一个通用隐私计算中间件平台。它解决的是数据协作中的核心悖论：

> **数据是资产，不流通则价值湮灭；流通则隐私失控。如何在原始数据不出域的前提下，让多方安全地交换数据价值？**

通睿的方案：每个参与方在自己的防火墙内部署一个**网关节点**（Gateway Node），节点在本地完成数据读取、分析与脱敏；**仅将脱敏后的计算结果**发送至协调节点（Coordinator）进行聚合。原始数据永不离开各自的可控环境。脱敏后的数据可安全地送入 AI 模型（LLM/ML）进行推理与决策增强。

### 1.2 关键原则

| 原则 | 含义 | 技术落地 |
|------|------|----------|
| **数据不出域** | 原始数据物理上不离开数据拥有者的网络边界 | 计算在节点侧本地执行 |
| **最小暴露** | 仅传输任务必需的最小化脱敏结果 | 输出白名单 + 暴露级别控制 |
| **可验证安全** | 客户可自行验证数据未被泄露，而非仅依赖厂商承诺 | 全链路审计日志 + 客户侧抓包验证 + 脱敏规则透明 |
| **价值可量化** | 每一次协作的价值增量可以被双方感知和量化 | 聚合分析报告 + 贡献度评估 |
| **AI 就绪** | 脱敏后的数据可直接输入 AI 模型，实现隐私安全的智能决策 | 标准化模型接口 + 推理沙箱 |

## 2. 问题陈述与价值主张

### 2.1 当前痛点

在多个行业中，存在共同的「数据协作两难」：

| 场景 | 协作需求 | 阻碍 |
|------|----------|------|
| 供应链风险评估 | 多家供应商共享经营数据，让核心企业评估整体供应链健康度 | 供应商不愿暴露真实营收、客户结构 |
| 同业联合风控 | 多家金融机构共享黑名单/欺诈特征，提升风控准确率 | 客户隐私法规限制，且不愿暴露自身客户清单 |
| 集团经营分析 | 子公司汇总经营数据到总部进行分析 | 子公司抵触——担心总部以数据为基准削减资源或干预经营 |
| 医疗多中心研究 | 多家医院联合分析罕见病数据，提升统计显著性 | HIPAA/GDPR/个保法——患者数据不能出医院 |
| 产业链协同 | 上下游企业共享库存/排产数据，优化整条链的交付效率 | 商业机密——库存水位、成本结构属核心竞争力 |

**共同特征**：各方**有动机参与协作**（能获得更好的分析/风控/优化效果），但**不信任其他方或平台方不滥用数据**。

### 2.2 通睿的解法

```
传统模式：各方把原始数据上传到中心平台 → 平台分析 → 返回结果
          ↑ 数据拥有者失去控制权，信任成本极高

通睿模式：各方本地部署网关 → 本地脱敏计算 → 仅脱敏结果离开 → 协调节点聚合
          ↑ 数据拥有者全程可控，信任由技术保证而非合同约束
```

### 2.3 价值主张（一句话）

> **让多方数据可以安全协作，价值对流，隐私不动。**

## 3. 用户角色与画像

### 3.1 角色定义

| 角色 | 身份 | 核心关切 | 使用频率 |
|------|------|----------|----------|
| **数据提供方管理员** | 部署网关节点的企业 IT/数据负责人 | 「我的原始数据真的没出去吗？」「脱敏规则怎么配？」 | 初次部署 + 规则调整（低频） |
| **数据消费方/发起人** | 发起分析任务的核心企业/研究机构 | 「能拿到什么颗粒度的结果？」「聚合结果可信吗？」 | 每次协作任务（中频） |
| **平台管理员** | 平台运营方（通睿团队或大客户内部 IT） | 「系统健康吗？」「哪个节点异常？」「审计合规吗？」 | 日常运维（高频） |
| **合规审计员** | 内审/外审/监管机构 | 「全链路可追溯吗？」「能证明数据未被泄露吗？」 | 定期审计（低频） |

### 3.2 用户故事

**数据提供方管理员**：
> *"作为一家供应商的 IT 经理，我想参与核心企业的供应链评估，但我需要 100% 确信我的原材料成本数据和客户名单不会泄露——无论是给平台方还是给竞争对手。我希望在参与之前就能看到系统要求暴露哪些数据、脱敏到什么程度，确认可接受后再加入。"*

**数据消费方/发起人**：
> *"作为核心企业的风控总监，我想评估 20 家供应商的财务健康状况。我不需要知道每家供应商具体卖给谁或赚多少钱——我只需要每家得到一个综合健康分和关键风险指标。我希望一键发起任务，5 分钟内拿到聚合报告。"*

**合规审计员**：
> *"作为外部审计机构，我需要在审计时看到完整的数据处理链路——从任务发起到结果返回，每一步谁做了什么操作、数据经过了什么变换。我需要抓包验证原始数据确实没有出域。"*

## 4. 核心使用场景

### 场景一：供应链健康度评估

1. 核心企业（发起人）在协调节点创建任务，选择 20 家供应商节点
2. 定义分析脚本：`supplier_health_score.py`（读取本地 ERP 数据 → 计算流动性/负债率/营收增长率 → 脱敏为 0-100 评分）
3. 脱敏规则：营收 → 分档（低/中/高），客户名称 → 伪名化
4. 20 个节点并行执行，各自返回脱敏后的评分
5. 协调节点聚合 → 输出「供应链健康度报告」：平均分 82，3 家低于 60 需关注，但不显示是哪家的具体营收数据

### 场景二：联合反欺诈

1. 三家银行各自部署网关节点
2. 任务：检查一笔贷款申请人的设备指纹/IP/关联账户是否在三家银行的历史欺诈库中出现
3. 脱敏规则：仅输出 `{"hit": true/false, "fraud_type": "string", "confidence": 0-100}`
4. 发起银行收到聚合判定：2/3 资料库命中欺诈特征 → 建议拒绝

### 场景三：集团经营分析

1. 总部发起月度经营分析任务
2. 各子公司节点运行 → 输出脱敏后的 KPI 仪表盘（毛利率分档、核心客户数量分档、产能利用率分档）
3. 总部看到聚合趋势，但无法反推单一子公司的精确数据
4. 子公司安心：产线停产等敏感事件不会暴露给总部以外

## 5. 功能需求

### FR-1：节点生命周期管理

#### FR-1.1 节点注册
- **输入**：节点名称、企业名称、管理员邮箱、SSL 证书 CSR
- **处理**：协调节点验证证书 → 分配唯一 node_id → 建立 mTLS 通道 → 返回注册令牌
- **异常**：证书无效 → 401；名称重复 → 409
- **输出**：`{node_id, token, mTLS_config}`

#### FR-1.2 节点心跳
- **频率**：每 30 秒
- **载荷**：`{node_id, timestamp, status, load_avg, disk_usage, active_tasks}`
- **异常处理**：连续 3 次无心跳 → 标记 OFFLINE → 通知平台管理员 → 该节点暂停接收新任务

#### FR-1.3 节点配置管理
- 脱敏规则配置：通过控制台添加/编辑/删除，实时生效
- 脚本白名单：仅允许执行已签名的脚本
- 资源配额：max_concurrent_tasks（默认3），max_cpu_cores（默认2），max_memory_mb（默认4096）

#### FR-1.4 节点注销
- **前置条件**：节点上无进行中任务（队列中任务已取消或迁移）
- **操作**：撤销 mTLS 证书 → 清理路由表 → 归档审计日志
- **数据处置**：节点本地数据由数据提供方自行处置，网关不保留副本

---

### FR-2：分析任务生命周期

#### FR-2.1 任务创建
- **输入**：
  - `target_nodes`：目标节点 ID 列表
  - `workflow`：执行模式（parallel / sequential）+ 超时时间（默认 300s）
  - `script_id`：已上传并签名的分析脚本
  - `input_params`：任务参数（key-value）
  - `required_exposure_level`：要求的最小暴露级别（L0/L1/L2）
- **校验**：目标节点在线 + 当前负载可接受 + 各节点暴露级别满足要求 + 脚本签名有效
- **输出**：`{task_id, estimated_duration}`

#### FR-2.2 任务分发
- 加密传输脚本 SHA256 签名 + 参数到各目标节点（mTLS 通道）
- 返回每节点 `task_step_id`
- 并发控制：单节点同时执行任务数 ≤ 配置值，超出则排队

#### FR-2.3 本地执行
- **执行环境**：Docker 沙箱容器
  - 只读挂载：`/data/` → 数据提供方指定的数据目录
  - 写入限制：仅可写 `/output/`
  - 网络：**完全隔离**，无出站访问
  - 资源限制：CPU 2 核，内存 4GB（可配）
  - 禁止：子进程创建、特权模式、宿主机路径访问
- **入口函数**：`def analyze(input_path, output_path, params) -> dict`
- **超时**：任务级超时可配（默认 300s），超时自动 kill 容器
- **失败处理**：自动重试 1 次 → 仍失败则标记 FAILED

#### FR-2.4 本地脱敏
- 网关拦截 `/output/` 所有写入操作
- 匹配脱敏规则 → 执行变换 → 验证变换结果 → 写入
- 未匹配规则的字段 → 执行**默认拦截策略**（不输出）
- 输出白名单机制：脚本声明期望输出字段 → 网关仅放行白名单内字段

#### FR-2.5 结果回传
- 脱敏后的输出以加密方式回传协调节点
- 格式：`{node_id, step_id, status: SUCCESS|FAILED|PARTIAL, output: {...}, execution_time_ms, sanitization_log: [{field, method, original_preview_hash, ...}]}`

#### FR-2.6 结果聚合
- 协调节点运行 `aggregator.py`（由发起人上传）
- 输入：所有节点的输出结果列表
- 输出：`{aggregate_result, per_node_details, completeness_score: 0-100}`
- `completeness_score` = 实际参与节点数 / 目标节点数 × 100

#### FR-2.7 任务状态机
```
PENDING → VALIDATING → DISPATCHING → RUNNING → AGGREGATING → COMPLETED
                                                    ↓              ↑
                                              PARTIAL (部分节点失败)──┘
                                                    ↓
                                                FAILED (全部节点失败/超时)
                                                    ↓
                                                CANCELLED (发起人取消)
```

### FR-3：脱敏引擎

#### FR-3.1 脱敏方法

| 方法 | 适用数据类型 | 变换方式 | 可逆性 |
|------|-------------|----------|--------|
| `pseudonymize` | 企业名、人名、身份证号 | 映射为临时 Token，同一实体跨任务 Token 一致 | 不可逆（无密钥无法还原） |
| `mask` | 手机号、账号、身份证 | 保留首尾各 2 位，中间 `****` | 不可逆 |
| `bucket` | 营收、金额、电量、产量 | 按配置区间映射为「高/中/低」或「区间A/B/C」 | 不可逆 |
| `generalize` | 地址、GPS 坐标 | 精确地址 → 区县级，GPS → 1km 网格中心点 | 不可逆 |
| `aggregate` | 数值型指标 | 输出均值/中位数/标准差而非原始值 | 不可逆 |
| `k_anonymize` | 多字段组合 | 确保输出结果中任意组合至少出现 k 次 | 不可逆 |

#### FR-3.2 脱敏规则配置
- 每个节点独立配置
- 配置结构：`{field_pattern: regex, method: string, params: {}}`
- 支持字段级（`revenue`）、类型级（`phone_number`）、正则级（`.*phone.*`）
- 规则优先级：精确匹配 > 类型匹配 > 正则匹配

#### FR-3.3 暴露级别控制
| 级别 | 允许输出 | 典型场景 |
|------|----------|----------|
| L0 | 仅数值评分（0-100） | 供应链健康分 |
| L1 | L0 + 聚合统计值（均值/分位数） | 行业对标分析 |
| L2 | L1 + 脱敏后实体级数据 | 联合风控（需看到命中类型） |

- **安全约束**：节点配置的暴露级别 < 任务要求的级别 → 任务拒绝（403），并明确告知差异
- **透明展示**：任务发起时可预览各节点的暴露级别，发起人据此判断是否可接受

#### FR-3.4 脱敏验证
- 每次脱敏后生成 `sanitization_log`
- 记录：原始字段名 → 匹配规则 → 变换方法 → 变换前后的数据指纹（SHA256 前 8 位）
- `sanitization_log` 随结果回传，供发起人和审计方验证

### FR-4：分析脚本引擎

#### FR-4.1 脚本规范
- **语言**：Python 3.11+
- **入口**：`def analyze(input_path: str, output_path: str, params: dict) -> dict`
- **返回值**：`{"status": "success", "data": {...}}` 或 `{"status": "error", "message": "..."}`
- **预装库**：pandas, numpy, scikit-learn, jieba, openpyxl
- **自定义依赖**：`requirements.txt`（仅允许纯 Python 包，禁止 C 扩展）
- **代码行数限制**：≤ 500 行（单脚本）
- **禁止行为**：文件系统遍历、网络调用、子进程、系统命令、动态代码执行（eval/exec）、读写非指定路径

#### FR-4.2 脚本管理
- **上传**：通过控制台或 API 上传 `.py` 文件
- **安全审查**：自动静态分析（AST 扫描）→ 禁止的函数调用 → 人工审核（高风险标记）
- **签名**：通过审查后 SHA256 签名，执行前验证签名完整性
- **版本管理**：保留最近 5 个版本，旧版本可回滚
- **模板市场**：预置 5-10 个常用分析模板（供应链评估、风控评分、经营分析、异常检测、相似度计算）

#### FR-4.3 沙箱网络隔离详解
```
┌─────────────────────────────────────┐
│           Docker Sandbox            │
│                                     │
│  /data/  ← 只读挂载（数据源目录）    │
│  /output/ ← 写入挂载（网关拦截层）   │
│                                     │
│  DNS: 无                             │
│  NET: none (完全网络隔离)            │
│  IPC: private                        │
│  PID: limited                        │
│                                     │
│  memory: 4GB max                     │
│  cpu: 2.0 max                        │
│  timeout: 300s max                   │
│  read-only rootfs: true              │
│  no-new-privileges: true             │
└─────────────────────────────────────┘
```

### FR-6：通信与安全基础设施

| 层面 | 方案 | 细节 |
|------|------|------|
| **传输安全** | HTTPS + mTLS 1.3 | 单一端口 8443；自签 CA + CRL |
| **身份认证** | JWT Token | 12 小时有效期；refresh token 30 天 |
| **权限控制** | RBAC 四角色 | admin / operator / auditor / viewer |
| **审计防篡改** | JSON 结构化日志 + HMAC-SHA256 签名 | 保留 90 天，支持导出第三方 SIEM |
| **密钥管理** | 节点侧密钥不落地协调节点 | mTLS 私钥仅存在于节点本地 |

## 6. 信任与透明机制

> **这是本产品的核心竞争力——不是「说安全」，而是让客户「看见安全」。**

### 6.1 信任架构的四个层次

```
┌────────────────────────────────────────────┐
│  L4: 监管信任 — 第三方审计可验证             │
│  → 全链路审计日志 + HMAC 验证               │
│  → 支持导出给外部审计机构                    │
├────────────────────────────────────────────┤
│  L3: 客户自主验证 — 客户可自行抓包验证       │
│  → 提供抓包验证工具/脚本                     │
│  → 脱敏日志可逐条比对                        │
├────────────────────────────────────────────┤
│  L2: 脱敏规则透明 — 客户全知全控             │
│  → 规则可视化配置界面                        │
│  → 每次执行展示匹配了哪些规则                │
├────────────────────────────────────────────┤
│  L1: 技术强制 — 代码保证而非承诺保证          │
│  → 沙箱网络隔离 (NET=none)                  │
│  → 输出白名单拦截 (未声明字段默认不传出)      │
│  → 暴露级别硬约束 (低于要求即403)             │
└────────────────────────────────────────────┘
```

### 6.2 客户自验证工具

| 工具 | 用途 | 交付物 |
|------|------|--------|
| `gateway-verify` CLI | 部署后验证环境安全性 | 一键运行 → 通过/不通过 (含不通过项明细) |
| 网络抓包验证脚本 | 在节点侧 tcpdump 抓包，验证只有加密流量到协调节点，无明文数据外泄 | Bash 脚本 + 解读文档 |

## 8. AI 模型集成方案

### 8.1 AI 的角色定位

通睿中的 AI 不是产品本身——AI 是**脱敏数据消费者**：

```
原始数据库 → 网关节点（本地读取）→ 脱敏引擎 → 脱敏结果 → AI 模型推理 → 智能输出
                                                          ↑
                                            原始数据永不进入 AI 上下文
```

### 8.2 支持的 AI 模型类型

| 模型类型 | 部署位置 | 用途 | 数据安全保证 |
|----------|----------|------|--------------|
| **节点侧本地 LLM** | 网关节点（GGUF 格式） | 对脱敏结果做分析摘要、异常解释、趋势描述 | 脱敏数据不出节点，在节点本地推理 |
| **节点侧本地 ML 模型** | 网关节点（ONNX/scikit-learn） | 评分、分类、异常检测 | 同上，沙箱内推理 |
| **协调节点 LLM** | 协调节点 | 聚合结果解读、报告生成 | 接收的是已被各节点脱敏后的数据 |
| **外部 LLM API** | 云端（可选） | 报告润色/格式化 | **仅当脱敏级别为 L0（纯评分）时允许**，否则禁止 |

### 8.3 本地模型管理

- **模型上传**：节点管理员通过控制台上传 GGUF / ONNX 文件
- **模型签名**：SHA256 签名，执行前验证
- **模型调用**：`gateway.infer(prompt, model="my-llama3", temperature=0.1)`
- **调用审计**：每次模型调用的 prompt 和输出记录在本地审计日志
- **模型权限**：模型绑定到节点，仅该节点的任务可调用

### 8.4 AI 安全约束

| 约束 | 规则 |
|------|------|
| **脱敏先行** | AI 模型**永远**只接收脱敏后的数据。网关在执行 apply_sanitization() 后才调用 infer() |
| **提示词安全** | 检测 prompt 中是否包含 `解密/还原/原始数据/真实姓名` 等绕过语，命中则拒绝调用 |
| **输出校验** | 对 AI 输出做正则扫描，检测是否包含疑似原始数据片段（如身份证号、手机号格式），命中则拦截 |
| **模型隔离** | 沙箱内运行的模型与外部网络完全隔离，防止模型通过隐蔽通道外泄数据 |

## 9. 安全架构

### 9.1 威胁模型

| 威胁 | 攻击者类型 | 危害等级 | 防御措施 |
|------|-----------|----------|----------|
| 恶意脚本窃取原始数据并编码到输出 | 发起人（恶意分析脚本） | 🔴 高 | 沙箱网络隔离 + 输出白名单 + 脱敏引擎拦截 + 静态代码审查 |
| 节点伪造成其他节点 | 外部攻击者 | 🟠 中 | mTLS 双向证书认证 + JWT 令牌绑定 node_id |
| 中间人拦截 | 网络层攻击者 | 🟡 中低 | TLS 1.3 + 证书固定（Certificate Pinning） |
| 协调节点管理员偷看脱敏输出 | 内部人员 | 🟠 中 | RBAC 权限分级 + 审计日志不可删除 + 脱敏输出本身已不可还原 |
| 重放攻击 | 外部攻击者 | 🟡 中低 | JWT 含 nonce + timestamp，服务端去重 |
| 脱敏规则被篡改 | 节点本地管理员（恶意） | 🟠 中 | 规则变更需审批 + 脱敏日志记录变更前后对比 |
| 侧信道攻击（时间/错误消息） | 高级攻击者 | 🟡 中低 | 统一错误响应格式 + 随机化处理时间 |
| AI 模型通过输出反推训练数据 | 模型使用者 | 🟡 中 | 输出二次校验 + 脱敏数据本身不可还原 |

### 9.2 纵深防御层次

```
Layer 1: 网络隔离
  └─ 沙箱容器 NET=none，无法外发任何数据

Layer 2: 文件系统控制
  └─ 只读挂载数据源 + 写入拦截层 + 白名单放行

Layer 3: 脱敏引擎
  └─ 字段级规则匹配 + 默认拦截策略

Layer 4: 输出校验
  └─ 脱敏日志 + 内容扫描（正则检测原始数据模式）

Layer 5: 传输加密
  └─ mTLS 1.3 端到端加密

Layer 6: 审计与追溯
  └─ 全链路日志 + HMAC 防篡改 + 不可删除
```

### 9.3 数据生命周期安全

| 阶段 | 安全控制 |
|------|----------|
| **读取** | 沙箱只读挂载，脚本无法修改源数据 |
| **处理** | 计算在隔离容器内进行，外部无感知 |
| **脱敏** | 网关拦截层强制介入，脚本无绕过可能 |
| **传输** | mTLS 加密，仅脱敏后的结果离开节点 |
| **聚合** | 协调节点内存中聚合，结果不落盘（可配） |
| **销毁** | 任务完成后沙箱容器及其文件系统立即销毁 |

|-------|--------|----------|
| AC-1 | 一键部署 | `docker-compose up` → 30s 内控制台可访问，节点注册可在控制台完成 |
| AC-2 | 多节点协作 | 发起 2 节点分析任务 → 各节点本地执行 → 脱敏聚合 → 审计日志验证原始数据未离开本地 |
| AC-3 | 脱敏效果 | 配置 `entity_name` 伪名化 + `revenue` 分档 → 输出中名称已 Token 化、营收已分档 → 节点侧抓包验证原始值不出现 |
| AC-4 | 离线容错 | 某节点离线 → 任务标记 PARTIAL → 在线节点正常完成 → completeness_score = 实际/目标 |
| AC-5 | 审计完整性 | 执行 3 个任务 → 导出审计日志 → 包含完整操作链路 → HMAC 验证通过 |
| AC-6 | 安全拦截 | 无证书节点连接被拒；无权限用户创建任务返回 403 |
| AC-7 | AI 模型调用 | 脚本调用 `gateway.infer()` → 传入脱敏数据 → 模型返回推理结果 → 输出不包含原始数据 |
| AC-8 | 暴露级别约束 | 节点配置 L0 → 任务要求 L2 → 任务拒绝（403）并返回明确错误信息 |

### 14.2 信任验收（客户视角）

| AC-ID | 验收项 | 通过条件 |
|-------|--------|----------|
| AC-9 | 客户自验证 | 客户运行 `gateway-verify` → 所有检查项通过 → 报告显示「环境安全，可加入协作」 |
| AC-10 | 脱敏预览 | 客户上传样本 CSV → 在控制台预览脱敏效果 → 预览结果与实际执行结果一致 |
| AC-11 | 抓包透明 | 客户在节点上运行抓包脚本 → 仅看到到协调节点的加密 mTLS 流量 → 无明文/无其他目的地 |
| AC-12 | 隐私仪表盘 | 任务完成后 → 客户在隐私仪表盘看到完整脱敏日志 → 可逐条比对 |
| AC-13 | 审计导出 | 客户/审计员可导出审计日志并独立验证 HMAC |

## 15. 约束与假设

### 15.1 约束

1. **网络**：节点需能出站连接到协调节点（443/8443），无需公网 IP
2. **容器**：节点侧必须安装 Docker 或 Podman
3. **Python 版本**：脚本需兼容 Python 3.11+
4. **无状态**：协调节点无状态（或仅缓存），所有持久化在 PostgreSQL

### 15.2 假设

1. **数据提供方诚实部署**：假设节点管理员不会恶意修改网关代码以绕过脱敏。防的是发起人/其他参与方，而非节点本地管理员
2. **网络可靠**：节点与协调节点之间网络可用性 ≥ 99%
3. **时钟同步**：各节点 NTP 时间同步，偏差 ≤ 5 秒
4. **数据格式**：数据源为标准结构化数据（CSV/JSON/数据库），非非结构化文档

### 15.3 明确的非目标（V1.0 不做）

- ❌ 非结构化数据（PDF/图片/视频）的隐私计算
- ❌ 基于硬件的可信执行环境（TEE/SGX）
- ❌ 多方安全计算（MPC）或同态加密
- ❌ 实时流式数据（仅支持批处理）
- ❌ 区块链存证

## 16. 附录：商业模式考虑

### 16.1 计费维度参考

此章节为草案，待与业务团队确认后细化。当前考虑的计费维度：

| 维度 | 说明 | 优势 | 劣势 |
|------|------|------|------|
| **按节点数** | 按活跃节点数收取月费/年费 | 简单透明，客户可预测 | 小节点和大节点价值差异无法体现 |
| **按任务量** | 按每月发起的分析任务数计费 | 按使用付费，灵活 | 客户难以预测成本 |
| **按数据量** | 按处理的数据规模计费（GB/月） | 公平反映资源消耗 | 计量复杂 |
| **分层订阅** | 基础版（5节点/50任务）→ 专业版（20节点）→ 企业版（无限） | 销售简单，客户分层清晰 | 需定义各层差异 |
| **混合模式** | 年基础订阅（含 X 节点 + Y 任务）+ 超出按量 | 兼具可预测性和灵活性 | 计费系统复杂 |

### 16.2 初步建议

**对于中小企业 → 分层订阅**（决策简单，销售成本低）
**对于大客户 → 年订阅（含定制节点数）+ 超出按量**
